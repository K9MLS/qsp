# ADR-0053: A server has three names, and they do different jobs

**Status:** accepted, 2026-09-08

Answers the question [ADR-0052](ADR-0052-qsp-is-federated.md) deliberately left
open: what a server's identifier should be. Rule 2 of that record requires
identity to be unique without a coordinator and to travel; this decides what
carries it.

## Context

**This is the one choice that cannot be changed once servers are running**,
because it is what everybody calls everybody else. Today a `qsp` link presents a
DMR ID in `repeater_id`, which is what the protocol carries, and 0052 recorded
that as a starting point rather than a conclusion.

The question felt stuck because it was the wrong question. "Is a DMR ID good
enough as a server's identity?" assumes one number should do every naming job a
server has. Look at what a DMR ID actually does on the wire: a station presents
it at registration, the far end looks up a password for it, and it appears in
the frame header. **That is a login.** A hotspot's ID does the same job in the
same packets.

Two requirements were being asked of one field, and they are opposites:

- A **credential** should be per link, revocable, and reissued freely. That is
  exactly what [ADR-0035](ADR-0035-per-peer-passwords.md)
  wants of a member's password and what 0288 built for a link.
- A **name** should be one per server, permanent, and never reissued to anybody
  else.

Three facts settled it, and all three came from running the thing:

- **`config.Validate` refuses two links sharing a `repeater_id`**, so a server
  needs one DMR ID per link it dials. Ten neighbours is ten IDs from a pool
  sized for people, each justified to a coordinator. A third instance needed two
  IDs for two links on 2026-09-08, which is how this surfaced.
- **A DMR ID is issued to an operator**, and a server outlives the person who
  registered it. A club running ten servers is not ten operators.
- **An administrator has to know what is connected at a glance.** `3132912`
  answers no question anybody asks. The operator's own proposal was
  `KD9EJA-01`, `KD9EJA-02`, or a name like `qsp-server-tx` — which is a display
  problem, not an identity one, and had been tangled with it.

## Decision

**A server has three names.** Each does one job and none does another's.

### 1. The identifier — what the software compares

Generated by the server at first run: 128 bits from `crypto/rand`, stored in
configuration, **never changed**. Unique without a coordinator, which is the one
property no issued number has and the one rule 2 demands. It costs nothing,
needs nobody's permission, and outlives the operator who set the server up.

**It is opaque and fixed length, and no code may parse meaning out of it.** Not
a prefix, not a checksum, not a length assumption anywhere but the one function
that validates it. This is the part that cannot be fixed later, and it is
written down because the next generation of this field is probably a public-key
fingerprint: 0052 rule 4 already records that anything a neighbour announces can
be false, and a random number proves nothing about who generated it. If the
identifier is opaque from the first day, swapping random bits for a fingerprint
is a generation change. If anything ever does arithmetic on it or assumes it
looks like a DMR ID, it is a redesign.

It is shown to an operator only where identity is the actual question — beside
two links with the same display name, or in a details view — and truncated. **An
identifier nobody reads is working correctly.**

### 2. The display name — what a human reads

Operator's choice, changeable, and what both consoles head a link with (0052
rule 2, as amended). `KD9EJA-01` follows the SSID convention from packet and
APRS and reads naturally to anyone who has been near AX.25: club at a glance,
instance number for which box. `qsp-server-tx` carries location instead of
ownership. Both are good and the operator picks; the console suggests the
callsign-and-suffix form in its placeholder, because a suggestion in the box is
worth more than a paragraph in a document.

**No code may parse the display name.** No deriving a club from the prefix, no
reading `-01` as an instance number, no sorting that assumes a shape. The moment
something does, the name stops being free to change — and it must stay free,
because a server moves from a garage to a rack and a club's naming settles after
it has been used for a while.

Two servers may choose the same display name and nothing prevents it. That is
acceptable **because it is not what anything matches on**; when it happens, both
consoles show the truncated identifier beside the name, which is impossible if
the name is all there is.

### 3. The DMR ID — a login, per link

Unchanged from what 0288 built: allocated by the listening side, one per link,
written into its registration list with a password against it, revocable by
withdrawing both. Ten logins for ten links is ordinary — a hotspot does not get
one ID per network it has ever joined either, it gets one per master it
registers with.

## Consequences we accept

**Nothing new on the wire to begin.** The homebrew identity packet already
carries what recognises a link today — the link name in `PackageID`, the
software string in `SoftwareID` — and the identifier travels the same way.

**A server that loses its configuration loses its identity**, and to its
neighbours it is a new server. That is the correct behaviour for a machine
rebuilt from nothing and the wrong one for a machine restored from a backup, so
a configuration export carries the identifier. Importing one is a **replacement**
rather than a clone: two servers claiming one identifier is the collision class
this project has met three times, and an import has to say so out loud. Backup
and restore gets its own record; this one only requires that the identifier be
part of what is exported.

**Renaming is free and re-identifying is not.** An operator may change a display
name whenever they like and the network does not notice. There is deliberately
no way to change an identifier, because "what everybody calls everybody else"
and "an operator can edit it" cannot both be true.

**A neighbour's claims are still claims.** An identifier announced over a link
is asserted, not proved, and rule 1 remains the answer: nothing a neighbour says
may make this server carry what its administrator has not permitted. The
fingerprint generation is what turns the assertion into evidence, and this
record's job is to leave room for it rather than to build it.

## What this does not decide

How the identifier is displayed when it must be — how many characters, and in
what form. Whether a later generation is a public-key fingerprint, and how a
network migrates if it is. How a backup is exported and imported, which is its
own record. Whether a display name is ever advertised beyond a server's
immediate neighbours, which belongs with the network view.

## Alternatives rejected

**A callsign as the identifier.** Tempting, because amateur radio already runs
on them and the operator proposed a callsign-based scheme. Rejected for the same
reason as a DMR ID and one more: **callsigns are reassigned.** A silent key's
call is reissued and vanity calls change hands, so an identifier could come to
mean a different person. It is the right thing for the display name, which is
what it is good at.

**A DMR ID as the identifier.** Issued to a person, scarce, one needed per link,
and requiring a coordinator — every property this needs, inverted. Kept as the
login it already is.

**A registry, including one QSP runs.** Any registry makes QSP something to be
admitted to, which is the thing it exists as an alternative to (0052 rule 1).
Self-generated identity is what makes "no headquarters" true rather than
aspirational.
